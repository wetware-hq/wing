# Prior art for the `.fleet` specification format

**Survey date:** 2026-10-20 (UTC)
**Scope:** existing, real frameworks and standards for declaring and operating fleets/swarms of autonomous software agents, and the adjacent scientific-workflow and model-card standards that cover the same ground.
**Evidence rule:** every row below carries a URL that was actually fetched on 2026-10-20. Where a release tag or date is given it came from the GitHub Releases API or the specification's own masthead, not from memory. Anything unverified is listed in the final section rather than described.

---

## Verdict

`NYESO1-A0201_v1.0.fleet` is substantially a re-implementation of three things that already exist, plus one part that genuinely does not. The execution graph, the typed inputs/outputs, the content-addressed replayability and the provenance-from-manifest requirement are **CWL plus Workflow Run RO-Crate**, and those standards do it better than we do: CWL already carries `checksum` (`sha1$…`) and `size` on every `File` object, already has `requirements`/`hints` with a fatal-error contract, already has an IANA media type (`application/cwl`), and Nextflow already content-addresses every task on a tuple that is a strict superset of our `(api_version, config_hash, target_hash, seed)` — it includes the container image, the conda/spack environment, the script text and the bundled scripts, all of which we are currently *not* hashing and all of which can silently change our results. The agent-facing half (who the agents are, what each is allowed to decide) is an **A2A Agent Card** plus an owners register. The document structure is a **model card** in the Mitchell et al. sense, rendered the way Hugging Face renders them: Markdown with structured metadata. The one piece with no clean prior art in any agent framework is the **human approval and spend-cap node placed inside the execution graph**. Approval gates exist, but almost always in application code (LangGraph `interrupt()`, ADK `require_confirmation`), not in the spec file; CrewAI's `human_input` flag is the only declarative approval gate found in a mainstream agent manifest, and the only declarative, machine-evaluable *spend cap* found anywhere is in a payments protocol (AP2 `payment.budget`), not in an orchestration framework. Scientific workflow languages are worse, not better, here: CWL explicitly puts "Pausing, resuming or checkpointing processes or workflows" **out of scope**. So: we are reinventing CWL + a model card + an agent card, and we should stop doing that; the approval/budget node is the real contribution and should be written as a *profile* on top of those standards rather than as a new file format.

The blunt corollary: `.fleet` as a **new file extension** is a mistake. Nothing we need requires one. What we have is a Workflow RO-Crate containing a CWL (or Nextflow) workflow, an RO-Crate metadata descriptor carrying the provenance, a `README.md` model card for the clinical prose, and an A2A-style card per agent. Four existing formats, zero new ones.

If we want the *declarative campaign manifest* idea validated by prior art, CrewAI's `crew.jsonc` + `agents/*.jsonc` split is the closest thing in existence to what we wrote, and it is a vendor format, not a specification.

That is a protocol-level human gate we could adopt verbatim instead of inventing one.

## 3. Workflow and provenance standards from scientific computing — the closer analogue

|---|---|---|---|---|

| **Workflow RO-Crate profile** (WorkflowHub) | The profile WorkflowHub uses to describe a workflow *as an object* (as distinct from a run of it). | RO-Crate profile | Live | https://about.workflowhub.eu/Workflow-RO-Crate/ |
| **Bioschemas `ComputationalWorkflow`** | Schema.org-based profile for marking up a computational workflow for FAIR discovery. | Schema.org / JSON-LD profile | `1.0-RELEASE` | https://bioschemas.org/profiles/ComputationalWorkflow/1.0-RELEASE |

**What each gives us that we are hand-rolling, specifically.**

- **CWL** gives us: the execution graph with typed data links instead of a mermaid picture and prose; `requirements` vs `hints` with a *defined failure semantics* (unsatisfiable requirement = fatal error, must not run) instead of our quality-gate thresholds being prose; per-file `checksum` + `size` instead of our four-tuple; `intent` as an EDAM IRI instead of a free-text target description; `$graph` packing so the whole campaign travels in one file. It also gives us a conformance test suite, which our format will never have.
- **Nextflow** gives us the **correct hash inputs**. Our `(api_version, config_hash, target_hash, seed)` omits the container/environment and the script text. Nextflow hashes both. Our replayability claim is therefore weaker than we have been stating: two runs with identical tuples can differ if the Boltz hosted model version changes underneath us — which is exactly the provenance gap already recorded in `boltz-version-2026-10-20.md`. Nextflow would hash the container; the hosted API gives us nothing to hash, so the honest fix is to record the API's own version string as a first-class hash input and to treat its absence as a known defect.
- **PROV-O + WRROC** give us the provenance model we are asserting in prose ("every output row replayable from the manifest hash") as an actual interchangeable graph, with a peer-reviewed profile and a SKOS mapping between the two. This is the single largest piece of avoidable reinvention in the document.
- **RO-Crate 1.2** gives us the packaging: one directory with `ro-crate-metadata.json` that holds the campaign manifest, the descriptor tables, the mermaid, the outputs and their checksums, and is citable by DOI. That is what `.fleet` is trying to be.
- **Bioschemas / Workflow RO-Crate** give us discoverability if any of this is ever deposited or published alongside the reproduction.

**What none of them give us:** CWL §3.1 lists, as explicitly out of scope for the specification, "Pausing, resuming or checkpointing processes or workflows" — alongside data security and permissions. So the approval gate cannot be expressed in core CWL at all; it would have to be a platform extension or a `requirements` entry of our own namespace.

**Reading.** Our document's shape — prose abstract over numbered sections, tables of measured performance, stated limitations, intended use — is squarely the Mitchell et al. model card, and the Hugging Face realisation (Markdown + YAML frontmatter) is exactly the file format we should have used instead of inventing an extension. Frontmatter would give us the machine-readable half (target id, version, api_version, hashes, owners) in the same file as the clinician-readable half, with existing tooling.

## 5. Human-in-the-loop approval and spend control as a first-class graph construct

**Reading.** This is the area where `.fleet` is least derivative — and where the prior art is thinnest and youngest. An approval gate as a *node in the declared graph*, with a spend cap attached to it, is not standard. CrewAI has the flag but not the cap; AP2 has the cap but it lives in a payments credential, not a workflow; ADK and LangGraph have the mechanism but in code; the scientific workflow standards have ruled the whole concept out of scope. If we want this to be more than a local convention, the defensible path is an **AP2-style constraint object (`amount_range`, `budget`) attached to a CWL step as a namespaced `requirements` entry**, which is exactly the extension mechanism CWL provides for semantics-changing extensions.

## What we should borrow

Ranked by how much hand-rolled work it deletes.

1. **Workflow Run RO-Crate + RO-Crate 1.2 for provenance and packaging.** Replace the prose "every output row is replayable from the manifest hash" with a WRROC profile crate. Peer-reviewed (PLoS ONE 19(9):e0309210), DOI-citable, with a published SKOS mapping to W3C PROV-O, and it bundles inputs, outputs, code and metadata as one object. This is the largest single piece of reinvention in `NYESO1-A0201_v1.0.fleet`.
2. **Nextflow's task-hash input list, as the definition of our content address.** Our tuple is missing the execution environment and the generator version. Adopt the superset — session, name, container/model identity, inputs, script, referenced globals, bundled scripts, stub flag — and where the hosted Boltz API refuses to expose a version, record that absence as a declared defect in the crate rather than letting the tuple imply a reproducibility we do not have.
3. **CWL `requirements` vs `hints` semantics for the quality gates.** Our descriptor thresholds are currently prose. CWL already defines the contract: an unsatisfiable `requirement` is a fatal error and the platform must not run the process, while an unmet `hint` is a warning. That is precisely the distinction between "do not submit this campaign" and "flag it". Free, and already implemented by every CWL runner.
4. **A2A Agent Card as the schema for the owners register.** Each fleet member gets a card with `skills`, `securityRequirements` and a JWS `signature`. This replaces "which agent or human decides each open question" with something a runtime can enforce and verify, and it is the Linux Foundation standard that ACP folded into — so it is the convergence point, not one of several options.
5. **Hugging Face model-card file shape: Markdown with a YAML frontmatter metadata block, as `README.md`.** Drop the `.fleet` extension. Frontmatter carries target id, version, `api_version`, hashes and owners machine-readably; the body stays the clinical abstract and system-card sections. Existing tooling renders and validates it; a new extension gets none.
6. *(Conditional, only if spend caps ever need to be enforced rather than described)* **AP2 `payment.amount_range` / `payment.budget` constraint objects**, attached to the approval step. Reuse the field names and the cumulative-evaluation rule even if we never touch AP2's payment rails.

## What appears genuinely absent

1. **An approval-and-spend-cap node as a declared element of an execution graph.** Nobody has this in one place. CrewAI has a declarative approval flag with no cap; AP2 has a declarative cap with no graph; LangGraph and ADK have the mechanism in code; CWL rules pausing out of scope entirely. The combination — a gate that is simultaneously a graph node, a monetary ceiling, and a provenance-recorded event — was not found in any surveyed system.
2. **Machine-readable quality gates with measured thresholds carried in the same artifact as the workflow.** CWL has typed IO and requirement semantics but no notion of "ipSAE top-1% enrichment AUC must exceed X"; model cards report measured performance but are not executable; no surveyed format binds the two.
3. **An agentic *system card* convention.** The genre exists as published prose (vendors publish documents called system cards), but no schema, profile or specification for one was located. The only machine-readable agent-level card is A2A's, and it deliberately describes capability and security, not evaluation, limitations or intended use.
4. **Provenance standards that cover a non-deterministic, versionless hosted model as a workflow step.** CWL hashes files and Nextflow hashes containers; both assume the compute is something you can pin. A hosted inference API that exposes no model version breaks the assumption underneath every provenance standard surveyed, and none of them has an answer for it. This is a real gap, and it is ours to document rather than solve.
5. **Any standard at all for a "fleet" as a unit.** Every agent framework declares *agents* and sometimes a *topology*; no surveyed standard declares a campaign with agents, budget, gates, provenance and clinical intent as one governed object. That concept is genuinely ours — which is an argument for writing it as a **profile over CWL + RO-Crate + A2A**, not as a fourth file format.
